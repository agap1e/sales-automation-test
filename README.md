# Заказы и выручка по артикулу и дню

Скрипт читает `sales.csv` и создаёт `daily_by_sku.csv` с колонками
`sku,order_date,orders,revenue`. Число заказов включает отмены, выручка — только
выкупленные заказы. В приложенной выгрузке получилось **13 798 заказов**
и **10 276 540,00 ₽ выручки**.

## Запуск

Нужен Python 3.10 или новее. Сторонних зависимостей нет, устанавливать ничего не нужно.
Все команды выполняются из корня репозитория:

```bash
python aggregate_sales.py
```

Результат появится в `daily_by_sku.csv` в текущем каталоге. Исходная выгрузка
включена в репозиторий под именем `sales.csv`, поэтому пример запуска сразу работает.
Если команда Python в вашей системе называется `python3`, используйте её вместо `python`.

Можно указать другие пути; каталог результата должен уже существовать:

```bash
python aggregate_sales.py --input "другая_выгрузка.csv" --output "результат.csv"
```

Денежные суммы считаются в целых копейках и выводятся с двумя знаками после точки.
Количество заказов — число уникальных `order_id`, а не сумма `quantity`.
Строки отсортированы по артикулу, затем по дате; отсутствующие пары не добавляются.

## Что обнаружено в данных

В исходном CSV 13 858 строк, 12 артикулов и 56 дат с 17 августа по 11 октября 2026 года.

- **60 лишних строк** — точные повторы заказов. После удаления повторов осталось
  13 798 уникальных `order_id`. Заказ учитывается один раз. Различающихся записей
  с одним номером в этой выгрузке нет.
- **35 нестандартных статусов**: `delivered ` — 11, `Delivered` — 7,
  `DELIVERED` — 7, `Cancelled` — 4, `CANCELLED` — 3, `canceled` — 3.
  Пробелы по краям удаляются, регистр приводится к нижнему,
  `canceled` заменяется на `cancelled`. Другие опечатки автоматически не угадываются.
- **4 пропуска quantity**, все у отменённых заказов: `1012637`, `1010495`,
  `1013303`, `1013394`. Эти заказы сохранены в `orders`, их выручка равна нулю.
  Количество не восстанавливается и не подменяется единицей.

Дополнительно скрипт проверяет заголовки, число полей, обязательные идентификаторы,
календарную дату и статус. Для `delivered` количество должно быть целым положительным,
цена — неотрицательной, с точностью не более двух знаков после точки.
Для отмен количество и цена не участвуют в расчёте и могут отсутствовать.
При неизвестном статусе, некорректных необходимых данных или конфликтующих записях
одного заказа скрипт завершается с ошибкой и номером строки, не выдавая частичный результат.
Имеющийся выходной файл при ошибке входных данных сохраняется.

## Как проверялся результат

```bash
python -m unittest discover -s tests -v
python verify_result.py
```

Прошли 9 тестов, в том числе проверки повторов, нормализации статусов,
отмен без количества, сортировки, точности денежных сумм, конфликтов заказов
и сохранения предыдущего результата при ошибке.

Отдельный `verify_result.py` не импортирует основной скрипт. Он загружает исходный
CSV в SQLite, убирает точные повторы через `SELECT DISTINCT`, затем считает
`COUNT(*)` и условную сумму `quantity × price` через SQL. С результатом сравниваются
все 631 строка, порядок строк и названия колонок, а не только общий итог.
SQLite входит в стандартную библиотеку Python, отдельная установка не требуется.

| Контроль | Результат |
| --- | ---: |
| Строк исходного файла без заголовка | 13 858 |
| Лишних повторов | 60 |
| Уникальных заказов и сумма orders | 13 798 |
| Выкупленных заказов после удаления повторов | 12 047 |
| Отменённых заказов после удаления повторов | 1 751 |
| Пар артикул и день | 631 |
| Сумма revenue, ₽ | 10 276 540,00 |
| UYT-0001 за 2026-08-17 | 28 заказов / 27 650,00 ₽ |
| UYT-0012 за 2026-10-07 | 2 заказа / 980,00 ₽ |

Контрольные равенства: `13 858 − 60 = 13 798` и `12 047 + 1 751 = 13 798`.
Результаты SQL-сверки и запуска тестов сохранены в `verification.txt`.
Повторный запуск основного скрипта даёт тот же CSV побайтно.

## Использование ИИ

Для подготовки кода, тестов и README использован ChatGPT. В ходе проверки
исправлены предложенные им черновые контрольные числа: они были заменены
значениями, полученными из исходного файла и подтверждёнными независимым
SQL-расчётом. Проверки не ограничивались текстовым ответом ИИ — код был запущен
на приложенной выгрузке и на тестовых примерах.

## Ограничения и допущения

Обязательные части задания выполнены. Принято допущение, что `order_id` обозначает
один заказ с одним артикулом, как в приложенной выгрузке. Если в будущем один заказ
будет содержать несколько товарных позиций или обновления статуса, потребуется
согласовать ключ позиции и правило выбора актуальной записи. Сейчас такие конфликты
считаются ошибкой, а не разрешаются выбором случайной строки.

Данные для дедупликации и агрегации хранятся в памяти; для данной выгрузки этого достаточно.
Независимый проверочный скрипт привязан к приложенному файлу и его целым ценам;
основной скрипт также поддерживает цены с копейками.

История разработки сохранена в Git. После распаковки архива её можно посмотреть
командой `git log --oneline`. Папка `.git` должна оставаться внутри проекта.
